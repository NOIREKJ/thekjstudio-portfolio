# 사업 공통 토대 — 문의·리드 파이프라인과 자동화

2026-11-22 · **착수 전 설계.** 무엇을 어떤 순서로, 무엇을 먼저 정해야 하는가.

수익 경로가 둘(KOINON 교회 플랫폼 유료 요금제 / 음악·편곡 판매)이고 둘을 받칠
공통 토대가 없다. 이 문서는 그 토대를 정의한다.

## 결론부터

**지금 사이트의 문의 폼은 작동하지 않는다.** 그리고 작동하던 때에도 알림이 없어
문의가 와도 알 수 없었다. 토대를 만드는 첫 가치는 "리드 관리" 가 아니라
**받는 경로를 되살리는 것**이다. 그건 Supabase 결제와 무관하게 지금 할 수 있다.

## 지금 상태 (2026-11-22 실측)

| 사실 | 확인 방법 |
| --- | --- |
| `inquiries` 테이블에 **행이 0건** — 생긴 뒤 한 건도 없다 | `select count(*)` |
| 폼은 브라우저에서 **PostgREST 로 직접 insert** 한다 | `src/routes/Contact.tsx` |
| 노션에 적힌 "기존 Resend 문의 폼" 은 **없다** — Resend 코드가 레포에 없다 | 전수 grep |
| Supabase 402(~12/10)라 **지금 모든 제출이 실패한다** | 폼이 `catch` 로 떨어짐 |
| 문의가 들어와도 **알리는 경로가 없다** | 테이블을 직접 봐야 함 |
| 제품 구분이 `type` 하나(commission·lesson·other) — **교회 문의 자리가 없다** | 스키마 |

### ⚠️ 그리고 보안 구멍

`inquiries` 의 RLS 정책이 `anon` 에게 **`with check (true)` 로 insert 를 완전히
열어** 두고 있다. anon 키는 배포된 번들에 들어 있는 공개 키다(원래 그런 키다).

폼의 스팸 방어는 **허니팟과 3초 타이머뿐이고 둘 다 브라우저 코드다.**
PostgREST 엔드포인트를 직접 때리면 둘 다 없는 것과 같다 — 누구나 무한히
행을 집어넣을 수 있고, 그게 무료 플랜 쿼터로도 돌아온다.

행이 0건인 건 운이 좋았던 것이다. 공개 폼이 있는 사이트에서 이 상태를 오래 두면 안 된다.

## 결정 1 — 브라우저가 DB 에 직접 쓰지 않는다

폼 제출은 서버 함수 하나(`api/inquiry.ts`, Vercel Function)를 거친다.
`anon` 의 insert 정책은 **떼고** service_role 만 쓰게 한다.

세 가지가 동시에 해결되기 때문이다.

1. **스팸을 실제로 막을 수 있다.** 허니팟·타이머 판정이 서버로 올라가고,
   IP 단위 속도 제한을 걸 자리가 생긴다. 클라이언트 방어는 방어가 아니다.
2. **알릴 곳이 생긴다.** 브라우저는 텔레그램 토큰을 가질 수 없다.
3. **402 일 때 흘릴 곳이 생긴다** (결정 2).

## 결정 2 — 받는 순간 세 곳으로. 저장은 그중 하나일 뿐이다

```
제출 ─▶ api/inquiry
         ├─▶ ① 텔레그램 자비스 봇   (즉시 알림)
         ├─▶ ② 메일               (영구 사본 · 본문에 payload JSON 그대로)
         └─▶ ③ Supabase insert    (되면 저장)
```

**①②가 하나라도 성공하면 사용자에게 성공을 보여준다. ③의 실패는 보여주지 않는다.**

이 시스템에서 치명적인 실패는 단 하나, **리드를 잃는 것**이다. DB 는 402·마이그레이션·
장애로 언제든 막힐 수 있고 실제로 지금 막혀 있다. 메일 본문에 payload 를 JSON 으로
그대로 넣어 두면 나중에 DB 로 **백필할 수 있다** — 메일이 임시 저장소 역할을 한다.

반대로 ①②가 모두 실패하면 **사용자에게 실패를 보여주고 다른 연락 수단을 안내한다.**
조용히 성공처럼 보이게 하는 것이 최악이다.

> 집 알림 구조의 원칙과 같다 — **판정은 서버가, 전달은 봇이.** 새 알림 채널을
> 만들지 않고 이미 있는 자비스 텔레그램 봇에 얹는다.

## 결정 3 — 테이블을 새로 만들지 않고 `inquiries` 를 지금 고친다

**0행이기 때문에 지금이 스키마를 자유롭게 바꿀 수 있는 마지막 시점이다.**
리드가 쌓인 뒤엔 같은 변경에 백필과 중단이 붙는다.

| 추가 | 왜 |
| --- | --- |
| `product` (`koinon`·`music`·`other`) | 교회 문의와 음악 문의는 응대도 주기도 다르다. `type` 하나로는 못 가른다 |
| `payload jsonb` | 제품별 질문이 계속 바뀐다. 컬럼으로 박으면 질문 하나 추가에 마이그레이션이 붙는다 |
| `stage` (`new`·`contacted`·`talking`·`won`·`lost`) | `handled` 불리언은 "연락은 했지만 아직 협의 중" 을 담지 못한다 |
| `source` | 어디서 왔는지(코이논 페이지·편곡 상세·직접). 어느 동선이 리드를 만드는지 알아야 한다 |

`type` 은 **남긴다** — 기존 폼 코드가 쓴다. `handled` 는 `stage` 로 승격하고
0행이므로 그대로 떼어낸다.

**검색·집계에 쓰는 것만 컬럼으로 올린다.** 교회명·교인 수 구간·관심 모듈처럼
목록에서 거르고 셀 값은 컬럼, 나머지는 `payload` 안에 둔다. 전부 컬럼으로 만들면
반쪽씩 빈 컬럼이 양쪽 제품만큼 쌓인다.

## 결정 4 — 이력은 따로 쌓는다 (`inquiry_events`)

상태만 들고 있으면 **언제 연락했는지가 사라진다.** 영업은 타이밍이 전부고,
"3일째 답이 없다" 를 판정하려면 마지막 접촉 시각이 필요하다.

append-only. 지우지 않고 쌓는다.

## 결정 5 — 이 테이블에는 공개 뷰를 만들지 않는다

리드에는 교회명·담당자 이름·전화번호가 들어간다. 사이트는 빌드 때 공개 뷰를
JSON 으로 구워 **저장소에 커밋한다** — 공개 뷰에 한 번 들어가면 깃 이력에 남는다.

편곡 작업에서 이미 한 번 냈던 사고다. 내부 기록을 공개 뷰 컬럼(`arrangement_note`)에
넣어 SSD 경로가 상세 페이지에 그대로 찍혔다.

그래서 규칙으로 못 박는다. **`inquiries`·`inquiry_events` 는 `public_*` 뷰를
만들지 않고, `fetch-content.ts` 의 `SOURCES` 에 절대 넣지 않는다.**
content-leak 테스트에 금지 목록으로 추가한다.

## 결정 6 — 개인정보는 법령 기준으로 받는다

교회명·담당자·연락처는 개인정보다. 폼에 **수집 항목·목적·보유 기간·동의 체크**가
있어야 하고 개인정보처리방침 페이지가 필요하다. 한국 개인정보보호법 기준.
(`korean-privacy-terms` 스킬이 Next.js 전제라 Vite 에 맞게 옮겨야 한다 — 확인 필요)

보유 기간을 정하면 **지우는 자동화도 같이 만들어야 한다.** 방침에 "3년" 이라
적고 안 지우면 방침을 어기는 것이다.

## 자동화 — 무엇을 돌릴 것인가

| 주기 | 무엇 | 왜 |
| --- | --- | --- |
| 즉시 | 새 문의 → 텔레그램 | 지금 없는 것. 가장 큰 구멍 |
| 하루 1회 | `stage='new'` 가 3일 넘은 건 → 텔레그램 | **실제로 돈을 잃는 지점.** 들어온 걸 잊는 것 |
| 주 1회 | 단계별 분포·신규·전환 → 아침 브리핑 한 줄 | 추세는 주 단위로 보면 충분하다 |

매출·구독 집계는 **넣지 않는다.** Patreon·결제 연동이 없어 셀 숫자가 없고,
빈 대시보드는 안 보게 된다. 결제가 붙은 뒤에 만든다.

## 단계

각 단계는 그것만으로 쓸 수 있어야 한다.

1. **폼 되살리기** — `api/inquiry.ts` + 텔레그램 + 메일. DB 없이 동작한다.
   **402 와 무관하게 지금 할 수 있고, 끝나면 문의를 다시 받는다.**
2. **구멍 막기** — `anon` insert 정책 제거, 서버 속도 제한.
3. **스키마 정리** — `product`·`payload`·`stage`·`source`, `inquiry_events`.
   DDL 은 402 중에도 적용된다(관리 API). 쓰기는 안 된다.
4. **문의 폼 확장** — 코이논 도입 문의(교회명·교인 수·관심 모듈·담당자).
5. **개인정보처리방침 + 동의 + 보유기간 삭제 자동화.**
6. **미응답 알림·주간 집계.**
7. **리드 보기 화면** — 어드민에 읽기 + 단계 변경만. 영업 CRM 을 만들지 않는다.

## 먼저 정해야 하는 것

- **①** 메일을 무엇으로 보낼 것인가. Resend 는 레포에 없다 — 새로 붙일지,
  텔레그램만으로 갈지. **텔레그램만 두면 단일 경로가 되어 결정 2 의 이중화가 깨진다.**
- **②** 리드 DB 를 어느 프로젝트에 둘 것인가. KJ Data App(`eiiifadgwbxfutallmsq`)에
  두는 쪽을 권한다 — 사이트가 이미 붙어 있다. 교회 DB 는 안 된다(교인 데이터와
  영업 데이터를 같은 RLS 아래 두게 된다). 다만 **둘은 같은 무료 조직이라 402 를 공유한다.**
- **③** 개인정보 보유 기간 — 방침에 적을 숫자. 정하면 삭제 자동화가 따라온다.
- **④** 코이논 문의에서 **금액을 묻지 않는다**는 전제 확인. 요금제가 미확정이라
  가격·모집 인원을 노출하지 않는 톤을 유지한다.

## 하지 말 것

- 브라우저에서 DB 로 직접 쓰기. 스팸도 알림도 402 도 전부 여기서 막힌다.
- `inquiries` 를 공개 뷰에 올리기. 한 번 커밋되면 깃 이력에 남는다.
- 리드가 쌓인 뒤에 스키마 고치기. **0행인 지금이 마지막 기회다.**
- 결제 연동 없이 매출 대시보드 만들기. 셀 숫자가 없다.
- 영업 CRM 만들기. 리드가 두 자리 수인 동안은 목록과 단계면 충분하다.
